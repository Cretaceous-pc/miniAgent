# AI Prompt 设计与问题解决记录

> 这是本项目里"提示词"这一层的设计说明，以及开发过程中真实遇到、定位、修掉的问题。
> 提示词分布在三处：`context/manager.py` 的系统提示词与摘要提示词，`tools/builtin.py` 的工具描述。

---

## 1. 系统提示词

完整原文（`context/manager.py` → `SYSTEM_PROMPT`）：

```
你是一个文档问答助手，工作方式必须遵守以下规则：

1. 你只回答根目录内文档能支撑的内容。先定位、再精读，不要凭空猜测。
2. 可用工具（按需组合，别一次把文档全读完）：
   - list_docs：看有哪些文档
   - outline：看单个文档的结构目录（带行号）
   - search_docs：跨文件按关键词定位，返回 路径:行号
   - read_doc：按行区间读片段
   - todo：多步任务先列计划，做完一步勾一步
   - calculator：计数/求和/比例一律用它算
   - remember：用户明确要求记住的稳定事实
3. 回答时给出依据：`文件名:行号`。找不到依据就直说"文档里没有"，不要编。
4. 工具返回 ERROR 时，读懂错误再决定下一步；同一工具同一参数连续失败 3 次会被硬性打断。
5. 回答用中文，简洁，先结论后证据。
```

**每条规则都是为了压住一种具体的失败模式**，不是"写好看"：

| 规则 | 压制的失败模式 | 怎么验证它起作用 |
| --- | --- | --- |
| 先定位再精读 | 不调工具直接凭常识作答 | 问"报销标准"时看是否先出 `search_docs`/`read_doc` |
| 别一次读完 | 上来就 `read_doc(1, 9999)`，把上下文预算吃光 | 看 trace 里 `read_doc` 的区间是否在几十到一百多行 |
| 必须给 `文件:行号` | 无法核对的结论 | 每轮回答是否带行号；不带就说明这条没生效 |
| 读懂 ERROR | 同一参数反复撞同一堵墙 | 制造越界路径，看它换参数还是重复 |
| 先结论后证据 | 长篇铺垫，答案埋在第三段 | 看回答首句是不是结论 |

### 迭代过程

- **v1**：`你是一个文档问答助手，请根据提供的文档回答问题。` → 实测出现两种坏行为：
  ①不调工具直接答；②调了工具但答不出处。
- **v2**：把"必须用工具 + 必须给行号"写成硬规则，并**列出工具清单**。
  效果：每轮回答都带 `文件:行号`；但也出现新的坏行为——把整个文件读完。
- **v3（当前）**：补"按需组合，别一次读完"和"找不到就说没有"。
  这一条是看到某个模型在没有对应文档时开始编"公司规定"之后加的。

**经验**：系统提示词里"禁止做什么"比"要做什么"更有效，但必须给出替代动作
（只说"别编"没用，要写"找不到就说文档里没有"）。

## 2. 工具描述也是提示词

工具描述会原样进模型上下文，所以写法和系统提示词一样重要。我的写法：

> 写"什么时候该用 / 什么时候别用"，而不是"这个工具做什么"。

`search_docs` 的实际描述：

```
在目录或单个文件里按关键词检索，返回 `路径:行号` 和命中片段。
适合"哪个文件提到了 X"。多个关键词用空格分隔；中文按 2 字片段匹配。
```

对比早期写法（实测效果差）：

```
搜索文档。参数 query 是搜索词。
```

差别在于：后者模型不知道该在"想知道有哪些文件"时用 `list_docs` 还是它；
前者直接把使用场景写进描述，模型的工具选择就稳定了。

**参数里给例子**也有效果。`calculator` 的参数说明是
`例如 (12+8)*3 或 avg([3,5,7])`，比只写"数学表达式"少很多格式错误。

**一个可观察的效果**：`search_docs` 的 `top_k` 默认 5，但在实际运行里模型会
自行把它调大到 10、20（问"哪些文档提到限流"那次是 `top_k=20`），
说明它读懂了"返回前多少条命中"这个描述。

## 3. 摘要提示词（上下文压缩）

`context/manager.py` → `SUMMARY_PROMPT`：

```
把下面的对话压缩成一段不超过 200 字的事实摘要，供后续对话继续使用。
必须保留：用户的目标与约束、已确认的结论（带文件:行号）、未完成的动作。
必须丢弃：寒暄、重复的中间过程、工具调用的原始输出。
已有摘要（可能为空）：{prev}

待压缩对话：{chunk}
```

三个设计点：

1. **给长度上限**（200 字）而不说"尽量简短"——后者基本无效；
2. **"必须保留"列三类**：目标、结论（带行号）、未完成动作。压缩最怕丢"用户到底要什么"；
3. **"必须丢弃"也写出来**，否则模型会把工具原文整段抄进摘要，等于没压。

实测产物（`sessions.summary`，窗口设成 1200 时触发的）：

```
用户目标：了解考勤规则。已确认：弹性上班09:00-10:30打卡均视为正常出勤（handbook.md:5）；
迟到超过3次/月，当月考勤系数记0.9（handbook.md:7）；年假3档：满1年5天、满3年8天、
满5年12天（handbook.md:11）。未完成：需查看api.md…
```

行号被完整保留，这是后续回答还能给出处的关键。

## 4. 问题解决记录

### 4.1 工具 Schema 没算进上下文预算（低估约 1k tokens）

- **现象**：trace 里 `context_tokens=323`，但同一次请求的 `usage.prompt_tokens=1354`。
- **定位**：把估算值和实际值打在同一行对比，而不是笼统"看看 token"。
- **根因**：7 个工具的 JSON Schema 每轮都随请求体发送，但它不在 `messages` 里，
  预算只统计了消息。窗口越紧越致命：会出现"估算没到预算、实际已被截断"。
- **修复**：`ContextManager.build(extra_tokens=…)`；调用方每轮把
  `est_tokens(json.dumps(tool_specs))` 传进去。
- **验证**：修正后估算 1373 / 实际 1347，误差 +2%（`tests/test_context.py` 有对应用例）。

### 4.2 压缩时按条删消息 → 请求 400

- **现象**：长对话触发压缩后，下一次请求直接被服务端拒绝。
- **根因**：OpenAI 协议要求 `assistant.tool_calls` 与随后的 `role=tool` 消息成对出现。
  按"消息条数"裁剪会把这一对拆开。
- **修复**：`group_turns()` 先把消息切成不可拆的轮组，压缩以轮组为单位丢。
- **验证**：`tests/test_context.py::test_group_turns_keeps_tool_pairs_together`。

### 4.3 思考路径不能回填给模型

- **现象**：思考型模型返回 `reasoning_content`，如果原样塞回下一轮 `messages`，请求 400。
- **处理**：思考路径只走"观测通道"（事件 → trace → 界面），**不进对话通道**；
  `tool_calls` / `content` 照常回填（协议要求）。
- **验证**：`tests/test_loop.py::test_reasoning_is_captured_but_never_echoed_back`
  同时断言三件事：事件里拿得到、库里没写、下一轮请求体里也没有。

### 4.4 `read_doc` 没有上限，一次把预算吃光

- **现象**：模型一次 `read_doc(1, 9999)`，单个工具结果就顶掉大半预算。
- **修复**：单次上限 400 行；越界自动收敛；返回末尾提示"还有 N 行，用 start=N+1 继续"。
  把"读多少"的决策交还给模型，而不是让它一次读完。
- **验证**：`tests/test_tools.py` 里对越界与截断有断言。

### 4.5 工具出错：抛异常还是回填？

早期是 `raise`，结果是用户看到一次崩溃、模型失去自纠机会。
改成把错误写成 `ERROR: 未知参数 pth；可用参数：path, start, end` 这样的 **tool 消息**回填，
模型下一轮就会改对参数。代价是循环里多一层 `except`，但纠错能力提升明显。

顺带把参数校验的报错顺序也调了：**先查"多余参数"再查"缺少必填"**。
因为模型拼错键名时，"未知参数 pth" 比"缺少必填 path"更能让它一次改对。

### 4.6 数字类问题必须过 `calculator`

提示词里写"计数/求和/比例一律用它算"，是为了避免模型心算错。
代价是多一次工具往返；收益是这类问题的答案可复核（trace 里有算式）。
`calculator` 本身用 AST 白名单求值，不用 `eval`，注入用例覆盖了
`__import__('os').system(...)` 这类输入。

### 4.7 docx 不引第三方依赖

`read_doc` 支持 `.docx`：`docx` 本质是 zip，正文在 `word/document.xml`，
用 `zipfile` + `ElementTree` 取所有 `w:p/w:t` 即可，不需要 python-docx。
**已知短板**：表格里的文字能读到，但行列结构会退化成一段段文本（`w:tbl` 没有单独处理）。

## 5. 已知限制

| 限制 | 现状 |
| --- | --- |
| PDF / xlsx / pptx | 明确报"不支持的格式"并列出支持项，不静默返回乱码 |
| 向量检索 | 用关键词 2-gram + 结构定位（`outline`）替代，好处是每一步可解释 |
| 并发 | 同步单线程；会话 `busy` 时拒绝新请求（409） |
| 规模 | 只在小型文档目录上验证过，万行级目录与超长对话未压测 |
